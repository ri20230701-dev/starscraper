# starscraper — 実装計画(確定版)

GitHub のユーザー名を入力すると、そのアカウントのリポジトリ群が **夜の 3D 都市** として生成され、
一人称で歩き回れる Web アプリ。静的ホスティングのみ、バックエンドなし。

この計画は Codex による敵対的レビュー(14 件の指摘)を反映した確定版。
レビューで却下・修正した判断は §12 に記録する。

---

## 1. 完了条件(done の定義)

1. `?u=<username>` 付き URL を開くと、その人の街が立ち上がる(性能条件は §8)
2. WASD + マウスルックで街を歩ける。**建物をすり抜けない**
3. 中央の照準を建物に合わせるとリポジトリ名 / star / 言語 / 最終更新が出る。決定キーで `html_url` を新規タブ
4. スクリーンショットボタンで、**画面と同じ見た目の**(Bloom が乗った)PNG が落ちる
5. `npm test && npm run build` が通る
6. 実ブラウザで 100 棟の街を目標フレームレート(§8)で確認済み

> 注: `npm run build` は `tsc --noEmit && vitest run tests/architecture.test.ts && vite build` であり
> **アーキテクチャテストしか走らない**。done 判定には `npm test` を必ず併記すること。

## 2. 非目標(意図的に捨てる)

- 認証 / OAuth / GitHub App / バックエンド / DB / 動的 OGP 生成
- Organization 対応、複数ユーザー比較、コントリビューショングラフ
- 街の永続化・スナップショット保存
- モバイルの Walk 操作(モバイルは Orbit のみ)
- **屋上アンテナ、地面への動的反射、導入の俯瞰旋回演出、fork 別棟の作り込み**
  → Walk を残すためのトレードオフとして削る(§12-1)

## 3. データ取得

`GET https://api.github.com/users/{user}/repos?per_page=100&sort=pushed&type=owner`(未認証)

- **1 ページのみ**取得する。続きの有無は本文の件数ではなく **`Link` ヘッダーの `rel="next"`** で判定し、
  Gateway の戻り値に `hasMore: boolean` を含める。表示は「更新順の先頭 100 件」と具体的に書く
- 使うフィールド: `name` / `stargazers_count` / `forks_count` / `language` / `pushed_at` / `fork` /
  `size` / `description` / `html_url`

### エラー・レート制限

- 404 → 「ユーザーが見つかりません」
- 403 / 429 → 応答を分類し、`Retry-After` または `X-RateLimit-Reset` に従って再試行を抑制。
  `X-RateLimit-Remaining: 0` 以外の二次制限も握りつぶさない
- リポジトリ 0 件 → 空の街ではなく専用メッセージ
- ネットワーク失敗 → 再試行ボタン

### 枠を無駄に減らさないための防御

未認証は IP あたり 60 req/h。ブラウザ直接取得なので全閲覧者で 1 枠を共有はしないが、
共有 NAT 配下では容易に枯れる。よって:

- **明示的なフォーム送信時のみ**取得する(入力のたびに叩かない)
- 同一ユーザー名の取得中リクエストは 1 本にまとめる(in-flight dedupe)
- 成功結果を短時間メモリに保持する
- **固定のサンプルデータを同梱**し、開発時の見た目調整と、レート制限時のフォールバック表示に使う

## 4. 街の文法(マッピング)

| リポジトリ属性 | 3D 表現 | 備考 |
|---|---|---|
| `stargazers_count` | 建物の高さ | **log スケール必須**。`h = base + k * log2(stars + 1)`。線形だと 1 棟だけ超高層で街にならない |
| `size` (KB) | 底面積 | log + 上下限クランプ。**§5 の区画幅制約を必ず満たす** |
| `language` | 外壁の色 | Linguist 準拠の**静的**カラーテーブルを同梱。未知/null はグレー |
| `pushed_at` | 窓の点灯率 | 直近 1 ヶ月 ≒ 90%、1 年放置 ≒ 10% に減衰。街の生死を表す演出の核 |
| `fork` | 低層・彩度低め | 色と高さの抑制のみ。別棟形状は作らない(非目標) |

## 5. 配置アルゴリズム

黄金角スパイラルは「花」になり街に見えないため不採用。**軸整列グリッド + 道路帯**。

1. `pushed_at` 降順にソート(同値は `name` 昇順で決定的に)。新しいものほど都心
2. 固定幅の区画セルを整列配置し、中心から渦巻き順にセルを埋める
3. **x / z 各軸で一定間隔ごとに道路帯を予約**する(渦巻きの走査順ではなく座標で決める)
4. **セル内のランダムオフセットは行わない**

制約(テストで保証する):
- 各軸で `最大建物幅 + 両側余白 ≦ 区画幅` — 建物が道路に侵入しない
- 道路帯が連結している
- 建物同士が重ならない
- 1 棟 / 少数棟 / 100 棟のいずれでも街として成立する

## 6. 再現性の契約

> 当初「同じユーザー名なら毎回同じ街」としていたが、これは成立しない。
> star / size / pushed_at は時間で変化し、窓の点灯率は現在時刻に依存するため、
> 乱数シードを固定しても出力は変わる(§12-2)。

正しい契約:

- **同じ入力データ + 同じ基準日時 + 同じ生成バージョン → 同じ街**
- 基準日時は `Date.now()` を内部で呼ばず、**純粋関数の引数で渡す**(domain は `Date` に触らない)
- 共有 URL は「最新状態の街」を表示する。過去の街の再現は非目標

## 7. 描画

### 窓(最大の技術リスク・最優先で潰す)

箱 1 個 + シェーダーで窓を描く。100 棟 × 数百窓を個別メッシュにすると即死するため。

**ハマりどころ**: 建物ごとに寸法が違うのに同じ UV グリッドを引き伸ばすと**窓も伸びる**。
- 面ごとに**実寸から窓の行列数を算出**し、窓サイズを全建物で一定に保つ
- 点灯/消灯は `(建物 ID, 面, 窓座標)` から決定的に決める(毎フレーム変わらない)
- 屋根面は窓を描かない
- 遠景のちらつき(モアレ)対策を入れる
- 参考: minesweeper の `src/presentation/three/BoardMeshes.ts` が標準材のシェーダー拡張を使っている
- **時間上限を設ける**。難航したら少数パターンの窓テクスチャ + `emissiveMap` に縮小する

### ポストプロセス

- `RenderPass → UnrealBloomPass → OutputPass` の順。**Bloom なしでは夜景にならない**
- トーンマッピング ACESFilmic。色変換とトーンマッピングの責任は後処理側にあるので、
  パス列を先に通してから材質の色を調整する
- 暗い空 + フォグ。地面は暗いラフメタル(**動的反射はしない**。必要なら発光パッチで擬似的に)

### 撮影

- 通常表示と撮影で**同じ最終描画関数**を使う。`renderer.render()` ではなく **composer 経由**。
  これを外すと Bloom の乗っていない画像が落ちる
- 撮影時は状態を進めず再描画して直後に PNG 化(`preserveDrawingBuffer` は常時有効にしない)
- 保存画像が黒くないこと・リサイズ後も正しいことを、日曜午後まで待たず確認する

## 8. 性能と測定条件

「3 秒以内」等を測定条件なしで書かない。

- 対象: デスクトップ Chrome / 有線または安定 Wi-Fi / 再訪(キャッシュあり)
- **通信待ちと描画開始を別々に計測**する。終点は「操作可能になった時点」
- 100 棟で目標フレームレートを定める(60fps を目標、下限 30fps)
- DPR は 1.5 上限でクランプ
- 品質切替は**固定プリセット**にする(自動フォールバックは作らない)
- WebGL 利用不可時の表示を用意する

## 9. 操作

- `Orbit`(デフォルト / モバイル): 街全体を回して見る
- `Walk`: PointerLock + WASD

### Walk の仕様(PointerLock 中はカーソルが消えるため)

- 選択は**画面中央の照準**で行う。DOM のホバーは使わない
- `Esc` で解除。フォーム入力・スクショ操作は**解除後**に行う
- 開始位置は道路上
- プレイヤーは半径を持つ。壁沿いに滑る移動を許す
- **衝突は移動先セルの参照で判定する**(グリッド配置なので一般 AABB スイープは不要、O(1))
- 低 FPS でのすり抜け防止に、1 フレームの移動量をセル幅以下に分割する
- ウィンドウのフォーカス喪失時にキー入力状態を解除する

## 10. 状態管理

ユーザー切替時の競合と資源解放を明示的に設計する。

- 取得リクエストに世代 ID を持たせ、**最新の要求だけを画面に反映**する(A→B と入力して
  B→A の順に応答が返ると、URL は B なのに A の街が出る)
- URL / 表示名 / 街データの三者を常に整合させる
- 街の再生成時に、旧メッシュ・材質・ジオメトリ・後処理資源・イベントリスナを破棄する責任者を決める
- 逆順応答と連続再生成の動作を統合時に確認する

## 11. アーキテクチャ

minesweeper と同じ 4 層 + AST ベースのレイヤ違反検知テストを踏襲する。

```
src/
  main.ts          # 依存注入(組み立て)だけを行う
  domain/
    model/         # Repository, Building, CityLayout
    services/      # heightOf, footprintOf, windowLitRatio, placeBlocks(すべて純粋関数)
  application/
    ports/         # RepositoryGateway
    usecases/      # BuildCity
    dto/           # CitySnapshot(Three 非依存)
    mapping/
  infrastructure/
    github/        # GitHubApiClient
  presentation/
    three/         # Scene, BuildingMesh, 窓シェーダー, Bloom
    input/         # WalkControls, OrbitControls
    hud/           # 入力フォーム、照準、ツールチップ、エラー表示
    ports/
```

**移植時の注意**: minesweeper の `tests/architecture.test.ts` は依存方向だけでなく、
`any` の使用、domain での `Math.random`、`GamePresenter.ts` 以外での RAF 所有も禁止している。
固有名・例外リスト・依存規則を **starscraper 用に書き換える作業を工数に計上する**。

守る契約:
- `three` を import してよいのは `presentation` のみ
- `presentation` は `domain` を直接 import しない(`application` 経由)
- `domain` / `application` で `window` `document` 等のグローバル禁止、`Date.now()` も禁止(§6)
- **描画ループの所有者は 1 つだけ**。名前を決めて architecture test の例外に登録する

**テスト方針**: 街生成(高さ・底面積・配置制約・点灯率・日時境界)、API 異常系、
`hasMore` 判定、建物とリポジトリの対応、Walk の非貫通を自動テストする。
ピクセル比較はしない。Bloom の見た目・操作感・PNG が非空であることは実ブラウザで確認する。

## 12. レビューでの裁定記録

1. **Walk を切れ(Codex 最優先提言)→ 部分的に却下。**
   工程に枠がない指摘は正しいが、Walk は GitHub Skyline との差別化そのもので、
   切ると「ライティングが綺麗な Skyline」になり目的(見せる)に反する。
   また建物はグリッド上に並ぶため衝突判定は移動先セルの O(1) 参照で足り、
   Codex が想定した一般 AABB スイープより安い。
   → **Walk を残し、アンテナ・地面反射・導入演出・fork 別棟を代わりに削る**(§2)。
2. **再現性の約束が成立しない → 全面的に受理。**§6 で契約を書き換えた。
3. **done 条件からテストが漏れる → 受理。**§1 で `npm test` を追加。
4. **地面反射は未計上の機能 → 受理。**§2 で削除。
5. 窓の寸法問題 / composer 経由の撮影 / `Link` ヘッダー / 非同期競合 / PointerLock とホバーの競合 /
   レート制限の二次制限 / architecture test の移植コスト / 測定条件の欠落 → すべて受理、本文に反映済み。

## 14. 進め方(技術リスクを前倒しする)

工程は「必須機能の初実装を最後の半日に残さない」順に組み替えた。

| | 内容 |
|---|---|
| 土曜午前 | **技術確認を先に潰す**: 固定 100 棟のダミーデータ → 窓シェーダー → Bloom → PNG 保存 |
| 土曜午後 | ドメイン層(配置・マッピング)+ テスト、GitHub 取得、入力フォーム、Walk と衝突、エラー処理 |
| **土曜終了時の判定点** | **主要体験が一巡していること。**未達ならここで追加要素を切る |
| 日曜午前 | ライティングと"映え"の調整(最重要) |
| 日曜午後 | 実機確認・修正・公開環境での確認(**予約枠。新規実装を入れない**) |
